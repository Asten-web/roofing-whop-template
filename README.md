# Summit Ridge Roofing — Whop Website template

Reusable residential-roofing website starter built for **Whop Websites**, React/TanStack Start, Whop Checkout Elements, and server-side Whop APIs. The default brand, price points, service area, and testimonials are sample content; replace them with verified business information before pitching as a live customer website.

> **Deployment/verification status:** this source package was prepared in an environment where external package installation and Whop account authentication were unavailable. It has **not** been deployed, a hosted `whop.app` URL has **not** been created, and no live/sandbox transaction or API write has been verified from this environment. Do not represent it as a deployed or tested site until the steps below are run successfully in a Whop account.

## Included

- Responsive home page with repair, replacement, and inspection services; service area; financing disclaimer; proof/trust checklist; example reviews labelled as examples; FAQ; contact details; estimate form.
- Three Whop plan slots and checkout buttons: $149 one-time roof inspection, $500 project deposit, and $399 illustrative flat-rate repair.
- Whop-hosted `CheckoutElement` and `ExpressCheckoutElement` checkout. An explicit card-payment fallback uses `CheckoutElement`; no custom card fields are used.
- Optional after-deposit card-on-file step using `Payments`, `PaymentElement`, `EmailElement`, and the required `BrandingElement`, then a server-created Whop setup intent. The setup intent is separate from the deposit and is intended to store a customer-authorized method without charging it.
- Estimate form submits to `POST /api/leads` with `account_id` and structured lead metadata.
- A restricted invoice operator page at `/admin`. It creates a Whop invoice via `POST /api/invoices`; manual `send_invoice` is default. An automatic-charge option is available only when a valid stored Whop payment method ID and payment token ID are present and explicit authorization covers the charge.
- `whop.track` events: `estimate_requested`, `service_viewed`, and `deposit_started`. The Whop-hosted site should provide automatic page-view and checkout tracking. The custom events also log a console entry for easy recording/inspection.
- No Stripe, PayPal, custom card-input fields, or copied roofing-company imagery.

## 1. Start from the official Whop Website scaffold

Use a machine with an internet connection and access to your Whop account. The Whop CLI documentation currently describes hosted default website addresses under `*.whop.site`; it does **not** guarantee a `whop.app` domain for a website. Verify the required domain in your Whop dashboard before promising a specific address. If the deliverable strictly requires `whop.app`, confirm that this is currently provisionable for your account; otherwise use the official Whop-hosted URL your dashboard provides.

Install the Whop CLI using the current official instructions at <https://docs.whop.com/developer/websites/quickstart>, then run:

```bash
whop apps init --app_type website --name "Summit Ridge Roofing" --domain summit-ridge-roofing
cd summit-ridge-roofing
```

Keep the `whop.app.json` / manifest and any Whop-generated project configuration from the scaffold. Copy this template's `src/`, `package.json`, `vite.config.ts`, `tsconfig.json`, `.env.example`, and `src/styles.css` into that generated project (merge/replace the matching starter files). If you choose another company name, change it in `src/config/site.ts` and in the `whop apps init` command.

Then install and run locally:

```bash
npm install
cp .env.example .env.local
# Edit .env.local using the guidance below.
whop apps dev
```

When the site works in local sandbox mode, deploy through the official CLI:

```bash
whop apps deploy
```

Use the exact hosted URL printed by the CLI or shown in your Whop dashboard. Set `APP_URL` to that exact HTTPS origin in the server environment after deployment, and redeploy if necessary. Do not claim a live URL until it opens and the deployed app has been tested.

## 2. Create the three Whop products and one-time plans

Create real products/variants in the Whop sandbox or business dashboard. The current CLI supports commands in this pattern (the exact product IDs are generated by Whop):

```bash
whop products create --title "Roof Inspection" --description "Photo-documented residential roof inspection" --visibility visible
whop variants create --product_id prod_REPLACE_ME --billing_type one_time --initial_price 149 --visibility visible

whop products create --title "Roofing Project Deposit" --description "Deposit applied to an approved roofing project total" --visibility visible
whop variants create --product_id prod_REPLACE_ME --billing_type one_time --initial_price 500 --visibility visible

whop products create --title "Standard Leak Repair" --description "Illustrative flat-rate minor leak repair; written scope and exclusions apply" --visibility visible
whop variants create --product_id prod_REPLACE_ME --billing_type one_time --initial_price 399 --visibility visible
```

Replace each `prod_REPLACE_ME` with the product ID returned by the preceding command. Copy the created **plan/variant IDs** into `VITE_WHOP_INSPECTION_PLAN_ID`, `VITE_WHOP_DEPOSIT_PLAN_ID`, and `VITE_WHOP_REPAIR_PLAN_ID`. Copy the company/business ID (`biz_…`) into both `VITE_WHOP_ACCOUNT_ID` and `WHOP_ACCOUNT_ID`.

Review the example pricing, flat-rate repair definition, refund/cancellation policy, deposit crediting, tax treatment, project terms, and state/local requirements with the real business before accepting money. A $500 deposit should not be collected until the customer has agreed to the project scope and deposit terms.

## 3. Configure server environment and API permissions

Set these values in the Whop Website app's server environment (and `.env.local` for local development):

```dotenv
WHOP_ACCOUNT_ID=biz_YOUR_BUSINESS_ID
WHOP_COMPANY_API_KEY=apik_YOUR_SERVER_SIDE_KEY
WHOP_SANDBOX=true
WHOP_API_BASE_URL=https://sandbox-api.whop.com/api/v1
WHOP_API_VERSION_DATE=2026-09-25
ROOFING_ADMIN_KEY=use-a-cryptographically-random-secret-with-32-or-more-characters
APP_URL=http://localhost:3000
```

For a deployed environment, set `WHOP_SANDBOX=false`, remove the sandbox API base override (or set the production API origin), and make `APP_URL` the exact hosted HTTPS origin. Do not expose `WHOP_COMPANY_API_KEY`, `ROOFING_ADMIN_KEY`, or any server API key under a `VITE_` variable. Never commit `.env.local`.

Use a sandbox company/API key first. Give the key only the scopes needed by the APIs your account uses. The Leads API documents `lead:manage`, `member:email:read`, `access_pass:basic:read`, and `member:basic:read`; payment verification, setup intents, and invoice creation/charging may require additional payment/setup-intent/invoice permissions according to the current Whop dashboard's scope list. Confirm these against your account's current API-key permissions before testing.

If desired, set `WHOP_LEAD_PRODUCT_ID=prod_…` to associate incoming estimate leads to a relevant Whop product. Leave it blank to create account-level leads.

## 5. End-to-end sandbox test checklist

1. Open the **Whop-hosted dev URL**. Confirm there are no missing plan/account IDs and that the inspection, deposit, and repair plan buttons open Whop checkout.
2. Use a sandbox-approved test payment method from current Whop documentation. Complete a test transaction with the Whop checkout UI; ensure the return callback supplies a Whop payment ID and the server verifies its status. Do not invent a success result in the browser.
3. Submit the estimate form with a valid test contact. Expect `POST /api/leads` to return HTTP 201 and a lead ID. Confirm the new lead in the Whop dashboard/API. A visible success message alone is not proof that the API write succeeded.
4. After a successful deposit, select **Save card for final invoice** and explicitly consent. Complete the Whop `PaymentElement` flow with `BrandingElement`; inspect the resulting setup intent and confirm Whop reports success and a payment method ID. The page's polling message is not a substitute for verifying the setup intent in Whop.
5. Open `/admin`, use the configured admin key, and create a **manual invoice** for a test customer and an agreed final-balance amount. Confirm the invoice is created in Whop and email/hosted payment link behavior is correct. Test automatic charging only in sandbox, only with valid Whop payment method/payment token IDs, and only after confirming the account's current API requirements and customer authorization.
6. In the browser console, trigger the estimate form, service CTA, and project deposit CTA. Check for `[Whop pixel] estimate_requested`, `[Whop pixel] service_viewed`, and `[Whop pixel] deposit_started`; then verify those events in the Whop pixel/event tooling if available. Page views and checkout events are injected/recorded by Whop on the hosted website.
7. Check responsive layouts at narrow mobile width and desktop; test keyboard navigation, readable validation, and that no API secret appears in client bundles or browser requests.

## 6. Architecture notes and safeguards

- `src/lib/server/whop-api.ts` is the only server-side API wrapper. Public components call same-origin endpoints; they do not contain the Whop company API key.
- The invoice UI uses an admin secret as a minimal operator gate for this demo. For production, add proper staff authentication/SSO, role-based authorization, CSRF protections appropriate to your auth model, audit logging, webhook reconciliation, idempotent job/invoice records, and server-side validation for project status/remaining balance. Do not treat the shared admin key as a complete enterprise auth system.
- Whop's current invoice create schema shows line-item `unit_price` as a decimal currency amount and payment IDs under `pmt_…` / `payt_…` patterns; confirm the current API response shapes and accepted fields with sandbox calls before production billing.
- `api.verify.ts` checks status through Whop's API. For a production booking system, also reconcile asynchronously from signed Whop webhooks and make invoice/job creation idempotent.
- A setup intent stores a payment method; it does not by itself collect the final project balance. Any later charge needs applicable customer authorization and the current API's required identifiers/permissions.
